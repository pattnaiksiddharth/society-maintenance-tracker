# System Design Write-Up — Society Maintenance Tracker

## Complaint History Model

A `Complaint` document holds current state only: status, priority, assignment, resolution timestamp. Every status transition is additionally written as a separate, immutable `ComplaintHistory` document — `previousStatus`, `newStatus`, `actorId/actorName/actorRole`, an optional `note`, and a `createdAt`. This is an append-only event log rather than a mutable audit field, so it can't be edited after the fact and naturally supports a "timeline" view per complaint. The write happens inside the same request handler as the status update (`PATCH /complaints/:id/status`): the history row is created first, then the complaint is mutated and saved. These aren't wrapped in a Mongo transaction, so on the rare partial failure the two could theoretically diverge; given MongoDB Atlas's single-node reliability and the low write volume of a society complaints app, this is an acceptable trade-off rather than a correctness requirement, but it's worth flagging if the write path is ever moved behind a queue or made concurrent. History is indexed on `{complaintId, createdAt: -1}` for fast, chronologically-sorted retrieval per complaint. Resident and actor identity are denormalized onto both `Complaint` and `ComplaintHistory` (name, unit, role) alongside the normalized `ObjectId` reference — this trades a small amount of storage and eventual-consistency risk (if a user renames themselves, old records keep the old name) for read performance and API-response simplicity, since the frontend never has to join against `users` to render a complaint card or timeline entry. The priority-only update endpoint (`PATCH /complaints/:id/priority`) intentionally bypasses history — priority is treated as metadata, not a lifecycle event, so only status changes are audited.

## Overdue Detection

Overdue is computed at query time, not stored. Both `GET /stats` and `GET /complaints?overdueOnly=true` independently run the same predicate: `status != RESOLVED AND createdAt < now - 7 days`. This keeps the model simple — no background job needs to flip an "isOverdue" flag, and overdue status is always correct relative to the current clock rather than the clock at last write. The `Settings` collection already exposes a configurable `overdueThresholdDays` (default 7, admin-editable via `PUT /settings`), but the two overdue queries currently hardcode `7 * 24 * 60 * 60 * 1000` rather than reading from `Settings`. This is the one piece of the design that isn't fully wired end-to-end yet: the schema and the admin UI toggle exist, but the read path doesn't consult them. Closing that gap is a single change — replace the literal with an `await getSettings()` call cached briefly per request — with no schema migration needed, since the field is already there. Once wired, threshold changes take effect immediately for every future query with no reprocessing of existing complaints, because "overdue" is a derived property, not stored state.

## Photo Handling

When a resident attaches a photo, the frontend reads the file with `FileReader.readAsDataURL()`, client-side-caps it at 5MB, and submits the resulting base64 data URI directly as the `photoUrl` string field on the complaint — no separate upload endpoint exists. `cloudinary` is listed as a dependency and `CLOUDINARY_URL` is documented in `.env.example`, but no route currently calls it; photos are stored inline in the MongoDB document rather than in object storage. This is functionally fine for a small-scale demo — MongoDB's 16MB document limit comfortably fits a handful of 5MB-capped images — but it bloats document size, slows down list queries that don't need image data (the `GET /complaints` list response currently includes the full photo payload for every row), and doesn't get CDN caching or resizing. The natural next step, using the dependency already in the project, is: resident uploads to a new `POST /complaints/:id/photo` (or pre-signs directly from the client), the server streams it to Cloudinary, and only the returned CDN URL is persisted — turning `photoUrl` from a multi-megabyte string into a lightweight pointer.

## Notification Flow

Five event types are modeled in `EmailLog` — complaint created, status updated, priority changed, notice broadcast, overdue alert — with `to`, `subject`, `body`, `type`, and `sentAt`. `Settings` has an `emailNotificationsEnabled` toggle, and `nodemailer` plus full `SMTP_*` config are present in `.env.example`. In the current codebase, however, `EmailLog.create()` is never called from any live route — the only writer is the one-time `migrate.ts` seed script, which backfills historical log entries from the legacy JSON dataset. `GET /api/emails` (admin-only) is therefore an audit/history viewer over that seeded data, not a live outbox. No route sends real email today. Wiring it up is additive rather than a redesign: a small `mailer.ts` service wrapping `nodemailer.createTransport(SMTP_*)`, called from the three complaint/notice mutation routes (create, status-update, notice-broadcast) and from an overdue-check job, each call writing one `EmailLog` row alongside the actual send. Because the schema and admin toggle already exist, notification behavior can be enabled without any further data model change.
